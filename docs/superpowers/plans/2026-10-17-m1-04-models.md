# M1-04 Model upload, inspection, converter sandbox, registry, class config — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (inline) or superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** An admin uploads their own YOLO26 weights (`.onnx`, or `.pt` that is converted in a sandbox), sees the model's task and classes, activates a version, pins it to a camera, and chooses which classes that camera predicts.

**Architecture:** Model files live behind the `vision/storage.py` seam. An `.onnx` upload is inspected by a subprocess (`python -m app.vision.inspect`, `onnx` parses protobuf only, never executes code, never `torch`). A `.pt` upload is **never opened by the backend**: it is written to a spool folder on a volume shared with a `model-converter` container that has no network, a read-only root filesystem, CPU/memory/time limits and a non-root user; it converts to ONNX and writes a result file; the backend polls the result. No Docker socket is ever mounted into the backend.

**Tech Stack:** FastAPI + asyncpg, `onnx` (inspector subprocess only), Ultralytics + PyTorch CPU (converter image only), React.

**Spec:** `docs/superpowers/specs/2026-10-16-saas-launch-roadmap.md` §13 (9.1, 9.3, 9.4, 9.11); the "test before use" panel (9.2) and the model server contract (9.10) belong to M1-05, which needs a gateway-side model server.

## Global Constraints

- Upload formats `.onnx` and `.pt` only; max 500 MB; sha256 of the stored ONNX is the identity of a version.
- A `.pt` file is never loaded by the backend, the inspector, or any process with network access. The original `.pt` is deleted after conversion (success or failure).
- Task ∈ `detect | segment` at launch. YOLO26 end-to-end outputs: detect `[1, N, 6]` (x1,y1,x2,y2,score,class), segment `[1, N, 6+nm]` plus a prototype tensor `[1, nm, H/4, W/4]`. Anything else is rejected with an actionable reason (roadmap 9.1: "exported with `nms=True` from an older version; re-export with YOLO26 default settings").
- Class names come from ONNX metadata `names`, parsed with `ast.literal_eval` (never `eval`). If missing, the admin pastes one name per line; count must equal the model's class count, and both counts appear in the 422 message.
- Versions are immutable once saved (file, sha256, classes, task, imgsz, uploader). States: `draft → active → archived`. Activation needs a licence attestation (user + time stored). A pinned or archived version cannot be deleted.
- A camera pins one exact version. A pin or upgrade that drops a class used by an enabled vision rule of that camera is refused with 409 naming the rule (vision rules arrive in M1-06; the check is implemented against `class_config` today and the rule check is added there).
- Class settings: `enabled`, `names{th,en}`, `min_score` 0.05–0.95, `colour` (`#rrggbb`), `alert`. Only enabled classes are used downstream.
- New tables: fail-closed RLS, shape of `0017_cameras.sql`. Routes under `/api/v1/orgs/{org}/…`, non-member 404, write needs `config:write`, `_mutation_gate` on writes, audit row on every write.
- Converter limits: no network (`network_mode: none`), `read_only: true`, tmpfs for scratch, `mem_limit 3g`, `cpus 2`, `pids_limit 256`, `cap_drop: ALL`, `no-new-privileges`, per-job wall-clock limit 300 s enforced by the converter.

## Review Focus

1. A crafted pickle `.pt` that writes a file outside the output folder or opens a socket fails with no effect and a clear error. *(Task 4)*
2. An ONNX that is not a YOLO export (a classifier, a truncated file, a zip bomb-sized protobuf) is rejected with a reason; the inspector subprocess is time- and memory-limited. *(Task 2)*
3. Class-name count ≠ output class count → refused with both numbers. *(Task 2/3)*
4. Two admins activate/archive the same version at once → one wins, state never skips a step. *(Task 3)*
5. Deleting or pinning across orgs: org B cannot see, pin, or delete org A's model by id. *(Tasks 1, 3, 5)*

**Interfaces — Produces (all `/api/v1/orgs/{org}/vision/…`):**
- `POST models` `{name}` → `{model}`; `GET models`; `DELETE models/{id}` (409 `version_pinned`).
- `POST models/{id}/versions?filename=x.onnx|x.pt&notes=` raw body ≤ 500 MB → 201 `{version}`; `.onnx` is inspected inline → status `draft`; `.pt` → status `processing`, job written to the spool (`{job_id}.pt` + `{job_id}.json`), 202-style `{version}`.
- `GET models/{id}/versions`, `GET models/{id}/versions/{v}` (poll processing); converter results are ingested by a background task `ingest_conversions()` reading `{job_id}.result.json` (`{ok, onnx_path?, error?}`), which then inspects and moves the ONNX into storage.
- `POST models/{id}/versions/{v}/classes` `{names: [..]}` when the file had none (count must match).
- `POST …/versions/{v}/activate` `{attest: true}` → `active` (400 without attest); `POST …/archive`; `DELETE …/versions/{v}` (draft/failed only, or archived and unpinned).
- Storage key `models/{org}/{version_id}.onnx`; `sha256` computed while streaming.
