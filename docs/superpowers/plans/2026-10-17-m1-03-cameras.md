# M1-03 Cameras, frame sampler, frame relay — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (inline) or superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** An admin adds a camera (uploaded demo video looped as a live feed, or an RTSP URL) to a gateway and watches it live in the browser; the picture path is ready for a detector (plans 4–6) without being one.

**Architecture:** Cameras live in Postgres and travel to the gateway inside the existing `cfg` message (`cameras:[…]`). A `vision` thread inside `edge-bridge` (same image, same enrolled identity — spec §6.3 "sidecar", collapsed into one process) reads the video/RTSP at `fps_sample`, runs a `Detector` (this plan ships only `NullDetector`), JPEG-encodes, and publishes frames to MQTT. The backend subscribes, keeps a latest-frame buffer per camera, and serves MJPEG to browsers.

**Designer's calls (the spec left these open; roadmap §13 "V3 decision on frame channel"):**
1. **Frames travel over MQTT, not a new WSS.** The edge already holds an outbound authenticated MQTT session with a per-edge ACL, so no new token type or endpoint is added. Cost: ≤ 100 KB per message (enforced), QoS 0. Revisit if a plant needs > 10 fps × many cameras.
2. **Video download uses a capability URL**, `GET /api/v1/edge-media/{video_id}?sig=…`, `sig = HMAC-SHA256(DATA_SOURCE_KEY-derived key, f"{edge_id}:{video_id}:{sha256}")`. Not time-limited (cfg is only pushed on change, so an expiring URL would die); it is bound to one edge and one file hash, and deleting the video makes it 404.
3. **No ffprobe.** Container is sniffed from magic bytes (`ftyp` for mp4, EBML `1A45DFA3` for webm); duration/frame size are read by OpenCV on the edge.

**Tech Stack:** FastAPI + asyncpg, paho-mqtt, opencv-python-headless + numpy (edge), React + TanStack Query.

**Spec:** `docs/superpowers/specs/2026-10-15-data-sources-and-vision-design.md` §6.1–6.4, §6.6; `docs/superpowers/specs/2026-10-16-saas-launch-roadmap.md` §13.

## Global Constraints

- Every connection is opened from the plant side; the server never dials in.
- RTSP URLs contain credentials: sealed with `secretbox.seal` at rest, never returned by any API (`has_rtsp_url: bool` only), delivered only inside `cfg`.
- `cfg` is not retained (unchanged).
- `fps_sample` ∈ [0.5, 15], default 5. Frame JPEG ≤ 960 px wide, quality 70, ≤ 100 000 bytes or dropped.
- Video upload: admin only, mp4/webm, ≤ 200 MB, stored under `VIDEO_DIR/{org}/{id}` through one `storage` module.
- New tables: fail-closed RLS, shape of `0015_data_sources.sql`. Routes: `/api/v1/orgs/{org}/…`, non-member 404, write needs `config:write` (`_CONFIG`), `_mutation_gate` on writes, audit row on every write.
- Camera belongs to an edge in the same site (FK `(org_id, site_id, edge_id)`).
- Edge ACL adds only `publishClientSend {p}/vision/frame/+` and `{p}/vision/stat`.

## Review Focus

1. Upload of a non-video (renamed `.exe`/HTML) or a 201 MB file → 415 / 413, nothing stored. *(Task 2)*
2. Camera whose video was deleted or RTSP host is down → tile shows `error` with a reason, other cameras keep streaming; worker retries with backoff, never crashes the gateway. *(Task 4)*
3. Viewer of org A requests org B's stream or a replayed/forged signed URL → 404 / 401, no frame bytes. *(Task 5)*
4. Slow browser → server drops frames, memory flat (no per-viewer queue). *(Task 5)*
5. RTSP URL never appears in any API response, audit row, or log line. *(Tasks 3, 4)*

- Test: `tests/contract/test_relay.py`, `tests/integration/test_camera_stream.py`

**Interfaces — Produces:**
- `class FrameRelay`: `push(camera_id: UUID, jpeg: bytes)`; `latest(camera_id) -> (seq, jpeg) | None`; `async def frames(camera_id)` async-generator that yields only the newest frame after each `seq` it has seen (slow consumers skip, never queue). - `POST /api/v1/orgs/{org}/cameras/{camera}/stream-url` → `{url}` valid 60 s (HMAC over `camera:exp`); `GET /api/v1/orgs/{org}/cameras/{camera}/stream?exp=…&sig=…` → `multipart/x-mixed-replace`. `GET …/cameras/{camera}/snapshot` → latest JPEG (session auth).
- `stat` messages update `cameras.status/status_detail/status_at` (throttled to one write per camera per 10 s).
